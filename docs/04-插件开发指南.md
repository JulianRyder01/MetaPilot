# MetaPilot 插件开发规范

> **规范版本：1.5.1**（本文档即规范本体，可持续更新，见 §0 版本与演进）
>
> MetaPilot 的功能以插件形式启用。插件分为三类：**官方核心**（MetaPilot 本身，不可禁用/删除）、
> **官方插件**（官方开发，可选用/禁用，不可删除）、**用户自定义插件**（可开发、禁用、删除）。
> 本文档规定插件的开发方式、目录结构、元数据 schema、路由约定与前后端接入机制，
> 是插件开发的**唯一权威约定**（此前为「插件开发指南」，v1.0 起升级为规范）。

---

## 0. 版本与演进

- 本规范使用语义化版本（`MAJOR.MINOR.PATCH`），当前为 **1.5.0**。
- **向后兼容承诺**：
  - `MINOR` / `PATCH` 升级只做**新增与澄清**，不删除或改变既有字段/约定的含义；
  - `MAJOR` 升级可调整约定，但必须在本章登记「迁移说明」，且**旧版插件在过渡期内仍可加载运行**（见 §9）；
  - `plugin.json` 的字段**只增不删**；新增字段一律可选，缺省时回退到旧行为。
- **「规范兼容」的含义**：按旧版规范编写的插件在新版规范下仍能正常加载与运行。
  它**不等于**「API 路径永远不变」——插件自身的 API 演进属插件内部事务（需前后端同步，见 §6）。
- 变更记录：每次更新本文档，在文末「附录：变更记录」追加一行（版本、日期、变更摘要）。

## 1. 插件是什么：前后端双插件模型

MetaPilot 是 **Web 应用（React SPA + FastAPI 后端）**。浏览器中的前端没有本地文件系统/进程能力，
所有数据（库、进度、统计、AI、文件读写）都在后端。因此插件的形态与 Obsidian / VS Code 这类
**桌面应用插件**（插件跑在客户端进程内，自己读写本地数据）不同，采用 Web 平台通行的
**前后端双插件**模式（Grafana / Jenkins / WordPress 同款）：

| 组成部分 | 位置 | 职责 | 必需性 |
|---|---|---|---|
| 后端插件 | `backend/plugins/<plugin_id>/`（Python 包） | 提供 `/api/plugins/<plugin_id>/...` 端点与业务服务（数据、AI、文件读写等） | **必需**（只要涉及新数据/服务） |
| 前端插件 | `client/src/plugins/<plugin_id>/`（注册模块） | 注册页面路由、导航入口与 API 客户端，渲染 UI 并调用后端端点 | **必需**（要让用户在前端看到功能） |

**一个插件 = 一个后端包 + 一个前端注册模块**，用同一个 `plugin_id` 绑定：

- 后端插件由加载器扫描 `backend/plugins/` 自动加载，`PluginManager` 管理启用/禁用状态（持久化于 `backend/data/plugins.json`）；
- 前端插件由注册表（`client/src/plugins/registry.ts`）统一收集，`App.tsx` / `AppLayout.tsx` 据此渲染路由与导航；
- **启用状态以后端为准**：前端通过 `GET /api/plugins` 感知，禁用时用 `PluginGate` 组件展示提示。

> 边界：只读核心数据的纯展示插件可以只写前端注册模块；但只要涉及**新数据、外部服务、AI、
> 文件读写或任何后端能力**，就必须同时提供后端插件。禁止在前端伪造数据（mock）冒充插件能力。

## 2. 插件分类

| 分类 | source | 可禁用 | 可删除 |
|---|---|---|---|
| 官方核心（MetaPilot 本身） | `core` | 否 | 否 |
| 官方插件 | `official` | 可 | 否 |
| 用户自定义插件 | `user` | 可 | 可（`DELETE /api/plugins/{id}` 物理删除） |

> 清单顺序：`GET /api/plugins` 返回顺序固定为 **用户自定义 → 官方插件 → 官方核心**（官方核心排最后），
> 前端插件页分组展示与此一致。

## 3. 后端插件骨架（plugin.json 为唯一元数据源）

```text
backend/plugins/my_plugin/
├── __init__.py      # 定义 Plugin 子类 + plugin 实例（只写 id 与 register）
├── plugin.json      # 元数据唯一来源（id/name/version/source/specVersion/...）
└── routes.py        # 路由（带门禁）
```

### 3.1 `__init__.py`：类只承担行为

元数据一律写在 `plugin.json`，**Python 类中不要重复声明**（消除双源漂移）：

```python
# backend/plugins/my_plugin/__init__.py
from fastapi import FastAPI
from app.plugins.base import Plugin

class MyPlugin(Plugin):
    id = "my_plugin"            # 仍保留 id 作为最小标识（与目录名一致）

    def register(self, app: FastAPI) -> None:
        from .routes import router
        app.state.my_plugin = MyService(...)   # 挂到 app.state 供路由取用
        app.include_router(router)

plugin = MyPlugin()
```

### 3.2 `plugin.json`：schema v1.2

```json
{
  "specVersion": "1.1",
  "id": "my_plugin",
  "name": "我的插件",
  "version": "1.0.0",
  "description": "插件做什么",
  "author": "你",
  "source": "user",
  "depends_on": [],
  "tags": ["效率", "自定义标签"],
  "capabilities": {
    "my_plugin.xxx": { "label": "能力描述" }
  },
  "requires": [],
  "content_types": [],
  "collection_kinds": {
    "my_kind": { "labelKey": "core.library.kindNote", "icon": "FileText", "openRoute": "", "unitLabelKey": "core.library.unitDoc" }
  },
  "features": ["功能点 1", "功能点 2"],
  "icon": "Puzzle",
  "changelog": [
    { "version": "1.1.0", "date": "2026-08-01", "summary": "新增 xxx 能力" },
    { "version": "1.0.0", "date": "", "summary": "首个版本" }
  ]
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|---|
| `specVersion` | 否（缺省视为 `1.0`） | 本插件遵循的规范版本；高于加载器支持版本时打印警告但**仍尝试加载**（宽松兼容，见 §9） |
| `id` | 是 | 小写下划线，全局唯一；**目录名 = id** |
| `name` / `version` / `description` / `author` | 是 | 展示用元数据；`version` 为插件自身语义化版本 |
| `source` | 是 | `core` / `official` / `user`（用户自定义默认） |
| `depends_on` | 否 | 依赖的其它插件 id 列表（强依赖）；启用前会检查依赖已启用 |
| `tags` | 否（缺省 `[]`） | **自由字符串**（无白名单），第三方插件可自带任意标签；用于插件页与商店按标签筛选 |
| `capabilities` | 否（缺省 `{}`） | 本插件提供的能力：`{cap_id: {label, ...}}`。其它插件经**能力检测**（`PluginManager.capability_available`）使用，不写死插件 id（见 §5） |
| `requires` | 否（缺省 `[]`） | 本插件**需要**的能力 id 列表（可选依赖）：提供方插件未安装/未启用时对应功能不可用，但**不阻止插件启用**；清单返回 `missingCapabilities` 供前端提示 |
| `content_types` | 否（缺省 `[]`） | 本插件负责解析/渲染的**组件块类型**（如 `single_choice`、`interactive`）；核心 `.mpf` 解析据此反查 `requiredPlugin`，**不再写死映射** |
| `collection_kinds` | 否（缺省 `{}`） | 本插件负责的**集合类型**（kind → `{labelKey, icon, openRoute, unitLabelKey}`）：kind→打开路由由插件声明（如 course 声明 `/course/{id}`），核心经 `GET /api/collection-kinds` 合并下发，**核心不再写死 kind→路由映射** |
| `features` | 否（缺省 `[]`） | 功能列表（自由文本），插件页以徽标展示；替代旧版前端硬编码的功能表 |
| `icon` | 否（缺省 `""`） | lucide 图标名（如 `GraduationCap`、`FolderOpen`）；插件页图标动态解析，未知回退通用图标 |
| `changelog` | 否（缺省 `[]`） | 更新历史（roadmap）：`[{version, date, summary}]`，**时间倒序（最新在前）**；插件页「更新历史」按钮以时间线形式展示。`date` 可空 |

> 兼容说明：`plugin.json` 缺失或字段缺失时，加载器回退到 `Plugin` 类的默认属性
> （旧格式插件不写 `plugin.json` 也能加载，见 §9）。

### 3.3 启动与门禁

启动时 `app/plugins/loader.py` 扫描 `backend/plugins/` 目录自动加载，**无需修改 main.py**。
路由始终挂载，被禁用时由 `requires_plugin` 依赖返回 503 + 启用提示：

```python
# backend/plugins/my_plugin/routes.py
from fastapi import APIRouter, Depends
from app.plugins.base import requires_plugin

router = APIRouter(
    prefix="/api/plugins/my_plugin",
    tags=["my_plugin"],
    dependencies=[Depends(requires_plugin("my_plugin"))],
)
```

## 4. 后端路由约定（强制统一前缀）

- **所有插件路由统一挂载在 `/api/plugins/<plugin_id>/` 之下**，`plugin_id` 与目录名、`plugin.json` 的 `id` 三者一致。
- 一个插件可以在该前缀下挂多个子路由（如 `/api/plugins/course/progress`、`/api/plugins/course/ai`），
  但**不得**使用 `/api/<非插件命名空间>` 或与其它插件重叠的短前缀（如 `/api/kb`）。
- 每个路由都必须加 `requires_plugin("<plugin_id>")` 门禁。
- 插件不得占用核心命名空间（`/api/libraries`、`/api/collections`、`/api/documents`、`/api/sections`、
  `/api/blocks`、`/api/plugins`、`/api/health`、`/api/stats/core`、`/api/stats/widgets` 等核心路由）。

> 历史说明：v1.0 之前 course 插件曾使用 `/api/progress`、`/api/stats`、`/api/ai`、`/api/assets/courses`，
> knowledge_base 插件曾使用 `/api/plugins/kb` 短前缀；v1.0 起已全部迁入 `/api/plugins/<id>/` 统一前缀。

## 5. 访问核心能力

- `request.app.state.store`：`LibraryStore`，库/文档集/文档/小节/块 CRUD（见 `app/storage/store.py`）
- `request.app.state.progress` / `request.app.state.stats`：进度与统计（由 course 插件注册）
- `request.app.state.importer`：课程包导入/导出
- `request.app.state.ai_insight`：AI 洞察服务（InsightService：资源树/索引/检索/对话/洞察规划）
- `request.app.state.ai_gateway`：**统一 AI 网关**（核心 1.1.1，AIGateway：chat/embed/rerank + 用量统计）。
  插件应经网关发起 AI 调用（`await request.app.state.ai_gateway.chat(...)`），密钥/地址由核心持有（存 .env），
  插件拿不到明文；调用自动记录 token/次数/成本到「统计 → AI 用量」。云端服务商与内置本地模型（向量/对话/重排）
  均在设置页「AI 服务」配置；本地服务经 `request.app.state.local_servers` 管理下载与启停
- `app/services/ai_grader.py`、`app/services/minimax.py`：MiniMax 判题与通用 chat 调用
- `app/services/embedding.py`：本地 embedding provider（Qwen3-Embedding-0.6B）

插件把自己的服务挂到 `app.state.<plugin_id>`，路由经 `request.app.state` 取用；
插件间依赖通过 `depends_on` 声明，不直接 import 对方模块。

### 5.1 能力检测：插件间互操作不写死插件 id

规范 v1.2 起，插件间互操作应使用**能力（capability）**而非写死对方插件 id：

- 提供方在 `plugin.json` 声明 `capabilities`（如 `symlink.mounts`），加载器注册进 `PluginManager`；
- 使用方在 `plugin.json` 声明 `requires`（可选能力），运行时用 `PluginManager.capability_available(cap_id)`
  检测能力是否可用（提供方已注册且已启用），**不写死 `manager.is_enabled("symlink")` 这类插件 id**；
- 能力元数据可携带展示描述与跳转模板（如 `sourceTypeLabel`、`linkTemplate`），
  由使用方下发前端渲染，避免「一个插件里写死另一个插件的描述」。

规范 v1.5 起，能力还可绑定**服务对象**：提供方在 `register()` 中 `manager.register_service(cap_id, service)`，
使用方经 `manager.service_for_capability(cap_id)` 取用，**不直接读 `app.state.<plugin_id>`**：

```python
# 使用方（如 ai_insight 路由）：
from app.plugins.base import manager
svc.symlink = manager.service_for_capability("symlink.mounts")   # 能力不可用时为 None
```

## 6. 前端插件注册表与运行时动态加载

前端插件分两种接入方式：**内置注册模块**（官方插件）与 **运行时 frontend.js bundle**（第三方插件）。

### 6.1 内置注册模块（官方插件）

官方插件以**注册模块**形式静态登记到注册表，由 `App.tsx` / `AppLayout.tsx` 统一读取渲染：

```text
client/src/plugins/
├── registry.ts        # 注册表：内置插件静态收集 + 动态插件运行时合并
├── types.ts           # PluginFrontend 接口定义
├── runtime.ts         # 运行时加载器：加载 frontend.js、注册动态插件
├── course/            # course 插件：路由/导航/API 客户端
├── ai_insight/        # ai_insight 插件
├── themes/            # themes 插件
└── symlink/           # symlink 插件
```

每个内置插件注册模块导出：

- `routes`：插件页面的 `<Route>` 定义（页面组件放 `client/src/pages/` 或插件模块内）；
- `navItems`：插件贡献的顶栏导航项（`to` / `label` / `icon`，`icon` 可为 lucide 组件或图标名字符串）；
- `api`：插件后端端点的 API 客户端函数（真实调用 `/api/plugins/<plugin_id>/...`，**禁止 mock**）。

`App.tsx` 渲染核心路由 + 注册表收集的插件路由；`AppLayout.tsx` 渲染核心导航 + 插件导航。
插件启用状态由 `usePluginsStore`（`GET /api/plugins`）感知，禁用页面用 `PluginGate` 包裹。

### 6.2 运行时 frontend.js bundle（第三方插件，即插即用）

规范 v1.4 起，**任意第三方插件可带前端 UI，无需修改宿主前端代码**：

- 插件包内放 `frontend/frontend.js`（IIFE，使用宿主注入的全局 `window.React`）；
- 后端加载器/安装器检测到该文件后，`/api/plugins` 清单返回 `hasFrontend: true` 与 `frontendUrl`，
  并由 `GET /api/plugins/<id>/frontend.js` 托管（路径净化，仅允许插件目录内文件）；
- 前端 `runtime.ts` 在插件清单刷新时对**已启用且带 frontendUrl** 的插件动态 `<script>` 加载；
- bundle 执行时调用 `window.MetaPilotPluginRegistry.register({ id, routes, navItems, ... })` 注册前端能力，
  `App.tsx` / `AppLayout.tsx` 自动合并其路由与顶栏导航；`navItems.icon` 用 lucide 图标名字符串即可。

### 6.3 前端扩展点（核心页插槽，规范 v1.5 起）

核心页面提供**扩展点（插槽）**，插件把 UI 组件注册进对应扩展点，核心只渲染插槽、不内嵌插件组件：

| 扩展点 | 核心渲染位置 | 用途示例 |
|---|---|---|
| `blockRenderers` | 学习页 BlockRenderer | 课程插件注册题目/交互块渲染器；无渲染器时核心按 `content_types` 反查所需插件显示占位 |
| `importTabs` | 导入对话框 | 课程插件注册「课程包导入」tab |
| `librarySections` | 「我的库」页侧栏 | 软链接插件注册挂载分区 |
| `collectionActions` | 「我的库」页操作区/集合卡片 | 课程插件注册「新建课程」按钮与「转为课程」操作（`createLabel/createIcon/onCreate` + `convertLabel/canConvert/onConvert`）；回调经 `CollectionActionCtx` 拿到 prompt/confirm/navigate/refresh，真实调用后端 API，禁止 mock |
| `settingsSections` | 设置页 | 插件设置卡片 |
| `themeSections` | 主题选择面板 | 主题插件注册特色主题列表 |
| `i18n` | 全局词典 | 插件自带三语词典（`registerI18n` 注入，覆盖/补充宿主词典） |

```js
// frontend.js 注册扩展点与词典示例
window.MetaPilotPluginRegistry.register({
  id: "my_plugin",
  routes: [{ path: "/demo", Component: DemoPage }],
  importTabs: [{ id: "my_import", label: "my.tab", Component: MyImportTab }],
  i18n: { "zh-CN": { "my.tab": "我的导入" }, "en": { "my.tab": "My Import" } },
})
```

打包与安装：`plugin.json` + `__init__.py`（后端）+ `frontend/frontend.js` 打成 zip，
在插件页「上传」或商店安装即生效；前端刷新后路由与导航自动出现。
完整示例见 `examples/third-party-plugin/`。

> **宿主全局 i18n 桥（通用协议）**：第三方 `frontend.js` 无法 import 宿主模块；需要感知当前界面语言、
> 取词条或订阅语言变化时，可经宿主注入的全局 `window.MetaPilotI18n`：
> `getLang()` 返回当前界面语言（`zh-CN` / `zh-TW` / `en`）、`translate(key, params?)` 取词条
> （含本插件经 `registerI18n` 注入的词典）、`subscribe(fn)` 订阅语言切换（返回取消订阅函数）。
> 这是与任何具体插件无关的通用协议，桥本身不含任何插件内容；不安装任何插件时，核心没有任何与之相关的行为。

## 8. 强制性开发规范清单

- 插件 id 使用小写下划线，全局唯一；**目录名 = `plugin.json` 的 `id` = 路由前缀中的 `<plugin_id>`**。
- 元数据**唯一来源是 `plugin.json`**；`__init__.py` 只写 `id` 与 `register`。
- `plugin.json` 必须声明 `specVersion`（新插件）与 `source`（core/official/user）。
- `tags` 为**自由字符串**（无白名单），第三方插件可自带任意标签。
- 插件间互操作使用**能力检测**（`capabilities` / `requires` + `capability_available`），不写死其它插件 id 或描述。
- 路由前缀统一 `/api/plugins/<plugin_id>/`；每个路由加 `requires_plugin` 门禁。
- 用户插件可被 `DELETE /api/plugins/{id}` 删除（路径净化已内置）。
- 新插件必须写测试（`backend/tests/`，pytest + TestClient）；前端改动需 `tsc` 通过。
- 依赖写入 `backend/requirements.txt`，敏感配置走 `.env`（模板追加到 `.env.example`）。
- 完成一个功能点提交一次 commit（中文描述）。

## 9. 兼容性策略

- **旧插件无需改动即可加载**：`plugin.json` 缺 `specVersion` 视为 `1.0`；缺字段回退类属性；
  完全没有 `plugin.json` 的旧格式插件按类属性加载。
- **规范升级**：`MINOR`/`PATCH` 只增不删；`MAJOR` 变更须在本章追加迁移说明，并在过渡期
  保持旧字段缺省可用（宽松加载：`specVersion` 高于加载器支持版本时仅警告，不拒绝加载）。
- **API 路径演进**：插件自身 API 变更属插件内部事务，须后端与前端注册模块同步修改；
  如无特殊理由，保持 `/api/plugins/<id>/` 前缀稳定，避免破坏第三方客户端。

## 10. 插件商店（plugins-store）

MetaPilot 提供**插件应用商店**：独立部署的 `plugins-store/` 服务（FastAPI），存放插件包（zip）并对外提供
清单、下载、上传接口；主后端通过 `.env` 的 `PLUGIN_STORE_URL` 指向商店，插件页「插件商店」Tab 浏览/安装/发布。

- **部署**：`plugins-store/` 可独立部署在任意服务器（Docker 或裸机 uvicorn，见其 README.md），
  数据（`store/data/packages/*.zip` + `index.json`）随部署持久化。
- **商店 API**：`GET /api/store/plugins`（清单，含 tags）、`GET /api/store/plugins/{id}/download`（下载 zip）、
  `POST /api/store/plugins/upload`（上传，校验 plugin.json）。
- **主后端接入**（`PLUGIN_STORE_URL` 未配置时商店功能关闭，返回 400 + 提示）：
  - `GET /api/plugins/store/plugins`：拉取商店清单；
  - `POST /api/plugins/store/plugins/{id}/install`：下载并安装为本地 user 插件（运行时注册，立即生效）；
  - `POST /api/plugins/upload`：上传 zip 本地安装（不经商店）；
  - `POST /api/plugins/store/publish`：上传 zip 发布到商店（供他人安装）。
- **上传校验**：商店与主后端共用同一套校验（plugin.json 必填字段、id 小写下划线且防路径穿越、
  source 枚举、tags 为自由字符串、防 zip slip 解压）。
- **规范查阅**：`plugins-store/docs/04-插件开发规范.md` 为本规范副本，与主仓库 `docs/04-插件开发指南.md` 同步更新。

## 11. 扩展 MetaPilot 文件（.mpf）格式（规范 v1.0.1）

`.mpf` 是 MetaPilot 的**系统底层统一格式**（库文件本身就是 .mpf，导入导出也用 .mpf），文件头 `type`
字段区分内容类型。官方核心解析 `doc`（文档/课程）与 `canvas`（图表）基础结构；各插件可注册新的
.mpf 类型或声明组件块解析依赖（见 `backend/app/services/mpf.py`）。

### 11.1 格式骨架

```json
{
  "format": "meta-pilot",
  "formatVersion": 1,
  "type": "doc",                    // doc | canvas | 插件注册的新类型
  "name": "课程名",
  "description": "", "author": "", "version": "1.0.0",
  "createdAt": "", "updatedAt": "",
  // type=doc：库-文档集-文档-小节-块（collections 结构同 docs/02 与课程包 manifest）
  "library": { "name": "", "description": "" },
  "collections": [ { "kind": "course|note|kb|canvas", "name": "", "folders": [], "documents": [] } ],
  // type=canvas：与 JSON Canvas 规范 v1.0 对齐（nodes/edges）
  "canvas": { "nodes": [], "edges": [] }
}
```

### 11.1.1 图表（canvas）与 Obsidian .canvas 双向兼容

`type=canvas` 的 `.mpf` 内容与 [JSON Canvas 规范 v1.0](https://jsoncanvas.org/spec/1.0/)
完全一致：`.canvas` 文件顶层就是 `{ "nodes": [...], "edges": [...] }`（无 `format` 头），
`.mpf` 的 canvas 段原样保存该结构，因此打开/导入/导出双向互通：

- **导入**：`POST /api/mpf/import` 接受 `.canvas` 文件（顶层含 `nodes`/`edges` 即自动转换为
  `.mpf` canvas 存入 `kind=canvas` 集合）；库页「导入」对话框同时接受 `.mpf` 与 `.canvas`。
- **导出**：画布页可导出**原生 `.canvas` 文件**（Obsidian 可直接打开）或 `.mpf`。
- **字段**：节点四类型 `text / file / link / group` 与通用字段
  `id/type/x/y/width/height/color`（`color` 支持 hex 与预设 `"1"`~`"6"`）；边
  `id/fromNode/toNode/fromSide/toSide/fromEnd/toEnd/color/label`，端点默认
  `fromEnd=none`、`toEnd=arrow`。
- **编辑器操作**：节点拖拽（多选整体移动）/ 点击单选 / Shift 多选 / 空白框选、Delete 删除、
  Ctrl+C/V 复制粘贴（关联边随节点复制）、Ctrl+Z / Ctrl+Shift+Z 撤销重做、双击编辑、
  四边中点拖拽连线（箭头端点 / 颜色 / 标签可调）、节点颜色与分组标签编辑、滚轮平移 /
  Ctrl+滚轮缩放 / 空格拖拽平移 / 适应画布；空画布可在库页头部「新建图表」创建。

### 11.2 插件扩展点

```python
# 注册新的 .mpf 类型（validate 返回错误列表，空=合法）
from app.services.mpf import register_mpf_type
register_mpf_type("mindmap", "思维导图", validate_fn, required_plugins=["my_plugin"])

# 声明某组件块类型需要某插件才能解析/渲染（未解析项检测）
from app.services.mpf import register_block_requirement
register_block_requirement("quiz_card", "my_plugin")
```

- 插件注册新类型后，导入该类型 .mpf 时若插件被禁用，`parse_mpf` 返回「未知的 .mpf 类型」错误；
  块级依赖（`register_block_requirement`）则标记为 `unresolved`，前端按「插件警告/报错」设置提示，
  无法渲染的项目显示为原始数据（与现有未渲染组件占位一致）。
- 存储：库文件为 .mpf（doc 类型）；读取旧 .json 自动迁移为 .mpf。
- 导出：`GET /api/mpf/libraries/{lid}/export-mpf`、`GET /api/mpf/collections/{cid}/export-mpf`；
  导入：`POST /api/mpf/import`（.mpf 或 .canvas，.canvas 自动转换）。

## 12. 界面国际化（i18n）（官方核心 v1.1.0 起）

MetaPilot 官方核心自 **v1.1.0** 起内置轻量 i18n：界面支持 **简体中文（zh-CN）/ 繁体中文（zh-TW）/ English（en）**
三种语言，顶栏与设置页均可随时切换，偏好保存在浏览器本地。

### 12.1 前端词典机制（官方核心提供）

- 基础设施：`client/src/i18n/`（`useT()` / `translate()` + zustand persist 语言偏好，无第三方依赖）。
  - 组件内：`const t = useT()`，然后 `t("key")` 或 `t("key", { param })`（`{param}` 参数插值）；
  - 非组件环境（工具函数等）：`import { translate } from "@/i18n"`。
- 词典按**域**拆分：`client/src/i18n/locales/{zh-CN,zh-TW,en}/<domain>.ts`。
  - `zh-CN` 为**基础全量词典**；`zh-TW` / `en` 为**覆盖层**，缺失词条自动回退 `zh-CN`，再回退 key 本身；
  - 域即插件/页面域（`core` / `course` / `symlink` / `sys` / `common` 等），key 一律以 `域.` 前缀命名（如 `symlink.newFolder`）。

### 12.2 插件如何支持 i18n（约定）

- 插件 UI 文案一律走 `t()`，**禁止硬编码中文**（注释与后端返回数据除外）。
- 插件在前端注册模块中把 `navItems[].label` 写成 i18n key（如 `nav.stats`），顶栏渲染时自动取词条。
- 新词条 key 前缀 = 插件域，同步维护三个词典文件；`common.*` 通用词条（保存/取消/删除等）直接复用。
- 后端元数据（插件 `name`/`description`、统计组件 `title`/`description` 等）由前端渲染层用 i18n key 覆盖展示（如统计组件标题 `t("core.widget." + id)`），后端本身不存多语言。
- 官方核心 UI 词条集中在 `core` / `sys` 域；官方插件各自维护自己的域词典。

### 12.3 插件注册界面语言（动态扩充）（官方核心 v1.6.0 起）

核心 i18n 支持**动态语言注册**：第三方插件可经宿主 i18n 桥 `window.MetaPilotI18n.registerLang({ value, native }, dict?)` 注册新的界面语言：

- `value`：语言代码（如 `ja` / `ko` / `fr`…），`native`：该语言自述名（Globe 下拉 / 设置页语言选择展示）；`dict`：可选，该语言界面词典。
- 注册后顶栏语言切换与设置页语言选择**即时出现**该语言；`translate()` 按新语言取词条，未覆盖词条**回退简体中文**（再回退 key 本身）。
- 词典 key 与核心词典一一对应（`common.*` / `core.*` / `sys.*` 等域），可只覆盖部分词条；语言清单与词典通常由插件后端提供（如 `GET /api/plugins/<id>/ui-langs`），前端 bundle 加载后拉取并逐个 `registerLang`。
- **解耦约定**：核心与插件描述不得写死语言列表——语言随插件数据动态变化；插件卸载/禁用后动态语言不再注册，核心无残留。
