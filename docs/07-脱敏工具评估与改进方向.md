# 脱敏工具（desensitize 插件）评估与主流开源调研报告

> 范围声明：本文为**评估 + 调研 + 改进方向**报告，不改任何代码。代码评审基于
> `backend/plugins/desensitize/`（service.py / routes.py / frontend.js）、`backend/tests/test_desensitize.py`
> 与 `docs/06-去敏感信息插件.md`；开源调研与业界最佳实践信息为 2026-08 检索所得，标注了核实程度。

## 结论摘要

- 项目自研的 desensitize 插件**定位清晰、工程实现务实**：规则正则 + 本地小模型双层识别、PDF/图片真
  实涂黑、失败降级、有单测有文档，作为「本地小模型驱动的文档级脱敏工具」是合格的。
- 与主流开源工具相比，缺的是**策略多样性**（无 tokenization / 加密 / 假数据替换 / 结构化表脱敏）与
  **安全收尾**（PDF 未清理非正文层、无再扫描校验、无审计留痕）。
- 主流工具里**没有中文识别型脱敏的开箱即用解**：Microsoft Presidio 生态最全但默认英文；中文本多为
  「中文 NER + Presidio 框架」或纯规则的拼装路线——与本插件现状同构，说明自研路线选择合理。
- 改进方向按 P0/P1/P2 给出（见第四章），核心 P0 三项：PDF 元数据/隐藏层清理、替换后「再扫描校验」、
  审计留痕；均不改架构、可复用现有工具函数。

## 一、项目现状评估

### 1.1 能力边界与工作流

插件挂载于 `/api/plugins/desensitize/*`（`routes.py`），整体是业界标准的**三阶段确认式**流程：

```
analyze（识别） → 用户逐条确认 → apply / redact（脱敏入库或下载涂黑文件）
```

具体能力矩阵：

| 能力 | 说明 | 源码位置 |
|---|---|---|
| 文本/Markdown 脱敏 | 敏感串替换为 █ 黑块，返回替换区间 spans | `service.py` `mask_text`（252-293） |
| PDF 涂黑 | 带文字层按 `search_for` 精确定位涂黑；扫描件走 OCR 词坐标 | `redact_pdf`（575-609）、`_redact_scanned_pdf`（611-651） |
| 图片涂黑 | 整张或按矩形区域涂黑 | `redact_image`（689-714） |
| 文件提取 | PDF / docx / doc / txt / md / 图片（OCR） | `extract_pdf_text`（471-494）、`extract_doc_text`（520-544）、`extract_image_text`（546-571） |
| 批量导入 | 多文件后台线程逐文件「提取→识别」+ 确认后入库 | `start_import` / `_run_import`（186-224）、路由 205-264 |
| 模型管理 | ollama 状态/配置/拉取，模型名不写死 | 路由 `status`/`config`/`pull`（58-106） |

### 1.2 双层识别与降级设计

识别是「**规则优先 + AI 补充**、失败不阻断」的双层架构（`analyze_text`，307-343）：

1. **规则正则引擎**（`_regex_items`，379-431）：身份证 / 手机 / 座机 / 邮箱 / IP / 车牌 / 银行卡 /
   护照 / 统一社会信用代码（`_RE_PATTERNS`，42-52）+ 合同语境姓名 + 百家姓通用姓名 + 地址模式。
   处理了身份证与银行卡 18 位重叠占位、姓名去重、地址长度≥6 防误抓。
2. **本地小模型（ollama，默认 `qwen3.5:4b`）**：长文本按 800 字符切片并发识别（`_chunk_text` /
   `_ai_chunk`，345-377），JSON 输出经 `_parse_json` 稳健解析（支持 ``` 围栏剥离、花括号平衡截取），
   模型返回的 value 必须能在原文定位（`_locate`，452-467）才采纳，防止幻觉。
3. **降级**：AI 不可用 / 失败 / 输出为空时，规则结果照常返回（337-339）；模型方差由
   `temperature=0` 压制。

这套「AI 只负责输出 JSON 清单、具体替换由确定性工具执行、AI 结果必须回扣原文」的设计，恰好规避了
大模型输出不可枚举、不可随意改写的两大问题，是**值得保留的核心设计**。

### 1.3 做得好的地方（亮点）

1. **PDF 用 PyMuPDF 官方 redaction API**：`page.add_redact_annot(clip) + page.apply_redactions()`
   （604-605）会**物理移除**涂黑区底层文字（移除后 `search_for` 搜不到），不是简单盖黑块——这是很多
   自制脱敏工具最容易踩的坑（盖层≠清除），本项目是对的。
2. **扫描件 PDF / 图片涂黑后扁平化重建**（611-651）：OCR 词坐标定位 → 画黑块 → 以图像重建 PDF，
   天然不存在「底层文字残留」问题。
3. **测试用 FakeOllama 替换真实模型**（`test_desensitize.py`）：不依赖真实 ollama / 不联网，覆盖
   `mask_text` 多出现、区间尊重、路由、PDF 涂黑后不可检索、图片整张/局部涂黑。
4. **类型标签可扩展不写死**（`_TYPE_LABELS`，30-37）：未命中类型原样展示；模型名、服务地址全部可配
   （`routes.py` 的 `config`，83-94）。
5. **文档齐全**：`docs/06-去敏感信息插件.md` 画清了流程、API 表与「AI 与工具解耦」的分层说明。

### 1.4 缺口清单（按严重度，均定位到源码）

| # | 缺口 | 位置 | 影响 |
|---|---|---|---|
| G1 | **PDF 保存未清理非正文层**：`doc.save(buf, garbage=3, deflate=True)` 仅压缩，metadata / 书签 / annotations / 嵌入文件 / 未命中区域的重叠隐藏文本层都还在 | `service.py:607`（`redact_pdf`）与 649（`_redact_scanned_pdf`） | 涂黑区外仍可能带作者、标题、自定义字段等元数据；隐藏文本可被提取，「已脱敏」不彻底。NIST IR 8053 明确文件 redaction 需处理隐藏层与元数据 |
| G2 | **定位靠精确匹配**：`page.search_for(v)` 与 `_find_value_rects` 的 `joined.find(compact)` | `service.py:598`、676 | 跨行断词、「李  三」、全半角混排、OCR 错字等变异拼写漏判，造成「漏网之鱼」 |
| G3 | **无再扫描校验**：替换/涂黑后不重新跑一遍识别确认无残留 | 无对应代码 | 无法证明输出已脱干净，人工确认也只看到「条目」，看不到「漏的」 |
| G4 | **无审计留痕**：不记录「谁、何时、以什么规则/模型、处理了哪些文件、涂了哪些值」 | 无对应代码 | 合规（个保法/等保）与追责需要；出了问题无法回溯 |
| G5 | **格式保留 masking 的固有风险**：`mask_text` 用与原文**等长**的 █ 替换（287-290），保留长度/位置，且未做假数据替换 | `service.py:287-290` | 长度/前缀/结构残留可辅助攻击者缩小范围、枚举还原；发布场景更推荐整体替换或不可逆假数据 |
| G6 | **姓名/地址类规则误报**：百家姓 2-4 字独立词形（`_GEN_NAME_PATTERN`）、地址长度≥6 即采纳 | `service.py:67-69`、72-77、412-429 | 普通话语料里「张伟」「刘德华大厦」等可能误标；影响用户体验与「全选应用」的信任度 |
| G7 | **图片涂黑为纯矩形覆盖**：无 OCR 时整张涂黑（`full=True` 兜底） | `redact_image`（704-711） | 有 OCR 时按 `_find_value_rects` 矩形并集，会连带涂掉相邻词；无 OCR 时只能整张，可用性差 |
| G8 | **批量导入任务内存驻留**：`_IMPORT_TASKS` 进程内 dict，无过期清理 | `service.py:173-174`、235-248 | 长跑服务内存增长；重启丢失任务 |

## 二、主流开源工具调研

### 2.1 横向对比表

| 工具 | 识别方式 | 脱敏/匿名化策略 | 中文 | 结构化数据 | 部署 | 许可证 | 活跃度 |
|---|---|---|---|---|---|---|---|
| **Microsoft Presidio** | 正则/规则 + spaCy NER + 可接 transformers/LLM | replace / redact / mask / hash / encrypt / Faker / custom；含图片与结构化模块 | 架构多语言但**默认英文**，中文需自接模型 | ✅（presidio-structured：表/CSV） | pip / PySpark / Docker / K8s | MIT | ⭐~10.6k，活跃（data-privacy-stack 社区维护） |
| **Faker**（Python） | 无识别（纯生成） | 假数据合成（可作替换源） | ✅ zh_CN / zh_TW | 结构化 profile / CSV | 库 | MIT | ⭐~19.4k，极活跃 |
| **Datafaker**（Java） | 无识别（纯生成） | 假数据合成 | ✅ zh_CN / zh_TW | CSV/JSON/YAML/XML | 库 | Apache-2.0 | ⭐~1.8k |
| **pynonymizer** | 规则/字典 | 数据库 dump 匿名副本（替换+假数据） | 部分 | MySQL/SQLite dump | 库 | MIT | ⭐~116，小众 |

### 2.2 各工具要点与结论

- **识别+匿名化一体、生态最成熟的是 Microsoft Presidio**：插件式 recognizer + 最全的匿名化 operator
  集，且有 `presidio-structured` 处理表/CSV。但它**默认英文**，中文需要自己接中文 spaCy/transformers
  模型——这正是本插件「自研中文规则 + 本地中文模型」的定位所对应的生态空白。
- **假数据合成**是另一个赛道（Faker/Datafaker）：不识别已有 PII，只负责造真实感替换值；本插件的
  `mask_text` 目前只做黑块替换，可把「按类型生成假值」作为可选策略补上。
- **LLM 驱动的匿名化**（NeMo Anonymizer、text-extract-api、zink）是 2025-2026 的新趋势，中文泛化
  更好，但依赖大模型推理、成本与稳定性不如规则；与本插件「本地小模型 + 规则兜底」互为补充而非替代。
- **⚠️ 核实结论：`Apache DataSankey` 不存在**。检索 GitHub（`apache/datasankey`）返回 404，全站
  搜索 `datasankey` 0 结果；Apache 名下没有该归档项目，属业界误传/名称混淆。若指「日志脱敏」类工具，
  更接近的可能是集群日志匿名化方案而非数据脱敏库。

### 2.3 与项目定位的对照

| 维度 | 本插件 | Presidio | 结论 |
|---|---|---|---|
| 中文开箱即用 | ✅ 内置中文规则 + 中文模型 | ❌ 需自接模型 | 本插件在中文上反而更省事 |
| 策略多样性 | 替换/涂黑 2 类 | 6+ 类 operator | 短板，见第四章 P1 |
| 结构化数据 | ❌ | ✅ | 若未来要脱数据库表，可引入 presidio-structured 或 ARX，不必自研 |
| 部署复杂度 | 本机 ollama + 插件 | 服务/容器 | 本插件更轻，适合教学/单机 |

## 三、最佳实践与合规

### 3.1 脱敏技术不可逆性对比与场景选型

| 技术 | 可逆性 | 典型适用 | 关键风险 |
|---|---|---|---|
| 假数据合成 synthetic | 不可逆 | 测试/研发/培训数据集 | 需保分布真实、防推断 |
| 泛化 generalization | 不可逆 | 保留统计意义（NIST 800-188） | 过泛化损可用性；不足可再识别 |
| 格式保留 masking | 不可逆但**泄露格式** | UI 展示、客服视图 | ⚠️ 保留长度/前缀/校验位，可枚举关联还原 |
| 替换/黑块 redaction | 不可逆 | 文档发布、司法/监管材料 | 只盖层未除底层 ≈ 零防护 |
| 加密 encryption | 可逆 | 传输/存储静态保护 | 密钥丢失 = 永久不可用 |
| 令牌化 tokenization / vault | 可逆 | 多系统一致引用且需还原 | vault 是单点；映射泄露 = 全部还原 |

> 选型口诀：**业务确需跨系统一致引用且允许还原 → tokenization；只求发布/测试不可还原 → synthetic /
> 泛化 / 替换；可用性需求越低越应选不可逆方案**（GDPR 语境）。
> 本插件当前只有「格式保留 masking + 黑块」两类，且都是不可逆类——对『教学场景发布脱敏』够用，但
> 对『测试数据替换』缺假数据合成，对『可还原』缺 tokenization。

### 3.2 合规差异（GDPR / 中国个保法）

- **GDPR 假名化（pseudonymisation）**（Art.4(5)）：附加信息须**分开放置 + 技术/组织措施**防再关联，
  假名化数据**仍是个人数据**；只有达到「不可再识别且不可逆」的**匿名化**才脱离 GDPR 规制
  （Recital 26）。
- **中国《个保法》第 73 条**明确区分：**去标识化** = 不借助额外信息无法识别（可借助额外信息还原）；
  **匿名化** = 无法识别且**不能复原**；只有匿名化数据脱离个保法规制。
- 对本项目的含义：`mask_text` 黑块替换不可逆，属于**匿名化方向**（好）；但 PDF 若有元数据残留
  （G1）、文本若保留长度前缀（G5），则「不可复原」是存疑的，需要第四章的收尾措施才能支撑
  「匿名化」声明。另去掉姓名 ≠ 匿名化，发布敏感数据集还需再识别风险评估（k-匿名 / differential
  privacy，NIST SP 800-188）。

### 3.3 安全需求清单

1. **识别分层**：规则（低误报速）→ NER/LLM（补召回）→ 人工确认（保发布安全）。面向发布重召回+
   复核（漏一个=事故）；面向内部测试重低误报保可用性。
2. **处理**：格式保留 masking 用于低风险字段；高风险字段整体替换（保留长度/前缀/末几位会缩小候选
   空间，如「保留后 4 位 + 区号」可枚举到个位数候选）。
3. **redaction 必须移除非正文层**：仅画黑块不够，需移除 metadata / 隐藏层 / 书签 / annotations /
   嵌入文件，并对转换结果**再扫描确认**（NIST IR 8053）。
4. **审计留痕**：记录谁、何时、以何规则/模型、处理哪些文件、用了哪些值；审计日志**不得明文存敏感
   原文**。
5. **防二次识别**：发布数据集需 k-匿名/差分隐私评估，不能只依赖「去掉名字」。

## 四、改进方向（按优先级，均不碰代码，供后续排期）

### P0 —— 安全收尾（先做，成本低收益高）

| 改进项 | 改哪里 | 做法 | 预期收益 | 外部依赖 |
|---|---|---|---|---|
| P0-1 PDF 清理非正文层 | `service.py:607`（及 649） | save 前 `doc.set_metadata({})`、移除 annotations/bookmarks/embedded files；或导出到新 Document 再 save | 消除元数据/隐藏层泄露，支撑「匿名化」声明 | 无（PyMuPDF 自带 API） |
| P0-2 替换后再扫描校验 | 新工具函数 + routes | 涂黑后对输出重新跑 `regex_items`（可再加小模型）→ 报告残留；有残留在响应中 `warn` | 「脱敏是否干净」可证明、可提示 | 无（复用现有 `_regex_items`） |
| P0-3 审计留痕 | routes + service | 记录时间/IP/用户名（若插件体系有）/用到的 rules+model/文件数/涂黑条目数，写 JSONL 日志 | 可追溯、可追责 | 无 |

### P1 —— 能力补齐（对齐主流工具）

| 改进项 | 做法 | 预期收益 | 外部依赖 |
|---|---|---|---|
| P1-1 假数据（Faker 风格）替换策略 | `mask_text` 增加可选 `strategy: blackout / fake`；按 type 用 Faker `zh_CN` locale 生成替换值（姓名/手机/邮箱等），跨出现处**同一值保持一致** | 测试/再发布场景可用性大增，避免「全文黑块没法读」 | `faker`（轻量，纯 Python） |
| P1-2 泛化/部分掩码策略 | 增加 `strategy: partial`，如手机号保留后 4 位、身份证保留前 6 后 4，其余 █ | 需要「部分可读」人机场景 | 无 |
| P1-3 变异敏感串识别 | `_locate` / `search_for` 前对 value 与原文做「去空白、全半角归一」再匹配 | 修 G2，减少跨行/混排漏判 | 无（字符归一表） |
| P1-4 姓名/地址误报抑制 | `_GEN_NAME_PATTERN` 增加「常见非姓名上下文排除词」；地址规则引入行政区划词典（省/市/区名列表）校验 | 修 G6，降低「全选应用」误伤 | 无（内置词典） |
| P1-5 批量任务内存治理 | `_IMPORT_TASKS` 增加 TTL 过期清理 + 上限 | 修 G8 | 无 |

### P2 —— 长远演进（如要覆盖数据库/结构化）

| 改进项 | 做法 | 预期收益 |
|---|---|---|
| P2-1 结构化表格脱敏 | 集成 `presidio-structured` 思路（列名+类型→规则），或引入 ARX/anonypy 做 k-匿名 | 覆盖 CSV/表数据场景 |
| P2-2 可逆方案（tokenization） | 自建 value→token 映射（本地 SQLite/vault），跨文件一致 | 支持「可还原」业务需求 |
| P2-3 图片按词矩形精涂 | OCR 词坐标已有（`extract_image_text` 返回 words），把矩形并集替换为**精确到词的外接矩形**，避免连涂相邻 | 修 G7，图片可用性 |
| P2-4 再识别风险评估 | 对发布文本返回类型分布统计（如 k-匿名提示、每类敏感项数量），供用户评估 | 对齐 NIST 800-188 思路 |
